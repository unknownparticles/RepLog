# Spec Delta

## Purpose

使用户能在支持的移动浏览器中安装并离线使用应用，可靠保存个人训练、饮食和体重数据。提供可验证的备份、恢复及升级策略，让应用在网络中断、存储不足或页面更新时仍清晰表达数据状态并避免静默丢失。

## ADDED Requirements

### Requirement: GitHub Pages 子路径部署
系统 SHALL 能从 GitHub Pages 仓库子路径及自定义域名根路径启动，静态资源、应用安装地址和离线导航均限定在该站点路径。路由 SHALL 通过哈希地址支持直接访问与刷新，不依赖服务端路由回退配置；本地数据库按站点路径隔离。

#### Scenario: 项目站点直接刷新
- **WHEN** 用户访问仓库子路径下带哈希的分析或当日详情地址并刷新
- **THEN** 应用正常加载，图标、图表资源和 Service Worker 不请求域名根目录的错误地址

#### Scenario: 同一域名托管多个项目
- **WHEN** 同一 GitHub Pages 域名下另有应用或不同路径的 RepLog
- **THEN** 当前站点的业务库与缓存范围独立，不修改其他项目的本地记录

### Requirement: 关于页版本与构建信息
系统 SHALL 在关于页明确展示语义版本号、构建提交、构建时间、数据格式版本与数据库版本；导航或页脚同时显示应用版本。版本源唯一，备份记录相同版本；发布标签与声明版本不符时发布校验必须失败。

#### Scenario: 核对当前安装版本
- **WHEN** 用户打开我的页面中的关于区域
- **THEN** 可明确看到例如 v0.1.0 的版本号及构建来源，离线时也能查看

#### Scenario: 发布标签不匹配
- **WHEN** 发布标签为 v0.2.0，而应用声明版本为 0.1.0
- **THEN** 发布检查失败，不将该构建发布到 GitHub Pages

### Requirement: 可安装应用与浏览器使用
系统 SHALL 提供名称、图标、主题色、启动地址和独立窗口模式配置，并在安全来源运行。支持原生安装提示时展示安装入口，不支持时提供适用说明；不具备安装能力的浏览器仍可使用核心记录功能。

#### Scenario: 不同安装机制
- **WHEN** 用户分别在支持安装事件的浏览器和需手动添加主屏幕的浏览器打开应用
- **THEN** 前者可触发安装流程，后者可查看手动步骤，不展示无效的一键安装按钮

### Requirement: 首次准备与离线访问
系统 SHALL 在首次成功加载且本地库初始化、核心资源缓存完成后标记离线可用。之后离线重开可查看日历、动作、餐食、训练和全部周期分析，并创建、修改或删除本地记录。首次离线且尚未准备时说明原因。

#### Scenario: 健身房无网络
- **WHEN** 用户已看到离线可用，关闭页面、断网后从主屏幕重开
- **THEN** 可打开历史日期并完成训练和餐食记录，刷新后仍存在，不提示等待网络同步才能保存

#### Scenario: 首次缓存未完成
- **WHEN** 首次加载时核心资源缓存失败
- **THEN** 不标记离线可用，联网时仍可记录，并提供重试准备入口

### Requirement: 本地档案与时间单位
系统 SHALL 无需账号即可建立一个本地档案，初始化中文、设备 IANA 时区、周一起始及千克/克/千卡/分钟/公里单位。用户修改档案时区后新记录和今天边界按新时区计算，历史归属日期保持不变；输入和显示均注明单位。

#### Scenario: 旅行修改时区
- **WHEN** 用户更改档案时区后重新查看上周
- **THEN** 旧记录仍在原归属日期，新建记录默认采用新时区的今天

### Requirement: 体重日记
系统 SHALL 允许按日期记录一个正数千克体重和可选备注；同日修改替换原值，覆盖前显示旧值并确认。删除体重后图表及时更新，无测量日保留缺失。

#### Scenario: 同日修正体重
- **WHEN** 已有七十千克记录，用户提交同日六十九点八千克
- **THEN** 确认后该日仅保留六十九点八作为当前值，不在均值中重复计数

### Requirement: 保存可靠性与并发
系统 SHALL 仅在本地写入成功后显示已保存；多实体保存必须完整成功或完整失败。存储不可用或配额不足时保留当前页面输入并提供重试和导出入口；多标签编辑同一记录发生版本冲突时提示重新载入或另存，不静默覆盖。

#### Scenario: 存储配额不足
- **WHEN** 保存餐食时浏览器报告配额不足
- **THEN** 不新增半条记录、不显示成功，保留未提交内容，用户可导出已有数据并重试

#### Scenario: 两个页面编辑同一训练
- **WHEN** 两个标签打开同一训练，前者先保存，后者随后提交旧版本
- **THEN** 后者收到冲突提示，前者的数据保持完整；另存时生成独立草稿并保留内容

### Requirement: 完整备份导出
系统 SHALL 提供带格式版本、导出时间、应用版本和时区信息的 JSON 备份，包含本地档案、全部记录、草稿、目标历史、自定义及被引用的内置字典快照、收藏、模板和体重。导出必须来自一致性快照，并能在新环境恢复。

#### Scenario: 离线迁移浏览器
- **WHEN** 用户离线导出并在另一已准备好应用的浏览器导入
- **THEN** 全部业务记录、历史快照和草稿可恢复，统计结果相同，不依赖远程食物或动作接口

### Requirement: 安全恢复与格式验证
系统 SHALL 首先验证备份格式版本、字段类型、有限数值、日期、标识唯一性、引用完整性和业务约束，再预览记录数量与替换范围。首版仅支持完整替换；用户确认前不改动数据，失败时原库保持不变；未知较新版本拒绝导入。

#### Scenario: 备份不合法
- **WHEN** 文件含未知版本、重复标识、失效引用或非法营养值
- **THEN** 指出错误并拒绝导入，当前数据不变

#### Scenario: 恢复失败与取消
- **WHEN** 用户在预览中取消，或已确认的恢复因存储不足而失败
- **THEN** 当前库保持完整原状，不出现一半旧数据一半新数据

### Requirement: 更新与数据库迁移
系统 SHALL 在新版本就绪时提示更新，存在未保存输入或进行中训练时不得强制刷新。数据库变更必须具有可验证迁移路径，迁移失败保留原数据并阻止继续写入；清理应用缓存不得清理业务记录。

#### Scenario: 训练时发现新版本
- **WHEN** 用户正在记录训练且新版本已缓存
- **THEN** 页面继续可用，保存草稿后用户可主动更新，更新后恢复训练

#### Scenario: 迁移异常
- **WHEN** 数据库结构升级中断或校验失败
- **THEN** 数据恢复原状，显示可重试或导出备份的入口，不在不兼容结构上继续写入

### Requirement: 数据控制与隐私默认
系统 SHALL 默认将日志保存在当前浏览器，不向远程服务发送训练、餐食或体重；使用本地字体与资源。设置中提供存储说明、备份入口和清空数据功能；清空需输入指定确认文字并再次确认，取消时不改变数据。

#### Scenario: 清空本地数据
- **WHEN** 用户主动输入清空确认文字并最终确认
- **THEN** 清除全部个人记录与配置，回到首次初始化；不遗留可恢复的个人摘要缓存

#### Scenario: 访问核心功能
- **WHEN** 用户完成记录与查看报表
- **THEN** 没有承载个人日志的外部网络请求，备份文件仅在用户主动导出时生成
